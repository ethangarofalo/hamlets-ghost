# Implementation Status Ledger

This ledger separates what Hamlet's Ghost currently does from what it is
testing, previewing, or still only describing. It is meant to be read before
the README's higher-level claims.

Status meanings:

- `implemented`: live code path exists and is covered by tests or an operator-verified endpoint.
- `prototype`: code exists, but the behavior is partial, preview-only, evidence-light, or not yet a stable research capability.
- `aspirational`: documents, schemas, or intended workflows exist, but the repository does not yet provide a complete operating path.

| Feature / Claim | Status | Evidence |
| --- | --- | --- |
| Prompt compiler that diagnoses a task and emits a compiled prompt candidate | prototype | `server.py` implements heuristic task diagnosis and compilation trace construction in `_infer_prompt_compiler_diagnosis()` / `_build_prompt_compilation_trace()`; `server.py` also exposes `/api/experiment/compiler-compare`. Tests cover the raw-vs-compiled route and rule-evidence recording in `tests/test_lab_decision_matrix.py`. The downgrade is intentional: this is a traceable compiler preview and A/B harness, not yet a learned compiler with validated policy selection. |
| Three-evaluator panel with an independent Apollo lane | implemented | `agents.py` defaults Apollo to `hermes_cli` / `gpt-5.4`, computes `APOLLO_INDEPENDENT`, and exposes provider status. `server.py` returns Apollo in `/api/providers`. `tests/test_backend_hardening.py` verifies Apollo's default system prompt is distinct from Athena and that Apollo defaults to an independent panel. Live verification on 2026-04-22 reported Apollo as `hermes_cli / gpt-5.4`. |
| Cross-family evidence gating for rule promotion | prototype | `database.py` defines promotion thresholds including support packets, support families, active model families, and human decisive counts. Rule-evidence slices are recorded and characterized, and `scripts/promote_rules.py` can report proposals. The downgrade is that current evidence is sparse and fixture-sized; the schema and thresholds exist, but cross-family promotion is not yet backed by a substantial earned corpus. |
| Disagreement-based human adjudication workflow | implemented | `database.py` builds packet disagreement summaries across Muse, Athena, and Apollo; current queue readiness is Apollo-centered, requiring Apollo's decisive preference to conflict with Muse or Athena. `server.py` exposes `/api/review/disagreements` and POST review decisions. `tests/test_disagreement_reviews.py` verifies split-panel detection, saved reviews leaving the unresolved queue, revisit-later behavior, and Apollo-disagreement queue entry. |
| Seeded taxonomy of anti-patterns, quality signals, and evaluator failure modes integrated into review and generation context | prototype | `data/taste_memory.json` provides seeded vocabulary; `server.py` loads it for `/api/review/reason-tags`; `database.py` uses human review reason-tags for generator feedback summaries and prompt coaching. This is implemented as seeded vocabulary and feedback plumbing, but the taxonomy is not yet earned: concept pages still advertise `provenance: seeded`, `evidence_count: 0`, and low confidence. |
| Lab Research Council as a five-advisor independent-then-synthesis protocol | aspirational | `lab-research-council.md` specifies five advisor roles and an independent pass before synthesis. The implemented system is lighter: `database.py` stores council history/actions as JSON payloads, `server.py` summarizes current analytics into a council-facing payload, and tests cover structured council trigger/action routes. That is useful characterization support, but it is not the five-advisor protocol described in the council program. |
| Calibration metrics surfaced on the operator dashboard, including `constraint_recovery_rate` and `critique_help_rate` | aspirational | `docs/STATUS.md` explicitly says these are not live status metrics in the current public surface and appear only in analytics test fixtures. The live learning snapshot discusses constraint pass deltas and critique noise, but these named rates are not computed as trustworthy dashboard metrics. They should not be read as active learning signals. |
| Genesis and Theron as epistemically distinct rival generators | prototype | Genesis and Theron are first-class packet roles with different routing, prompts, and provider paths; paired packet tests cover both roles. The current lab also stores human `pair_distinctiveness` judgments and tags `same_writer` reviews as `voice_collapse`. The downgrade is important: there is no automated voice-distance metric or systematic evidence yet proving Genesis and Theron produce reliably distinct voices. |
